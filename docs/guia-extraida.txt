Guía de multiplicación de matrices en C y Go
Entorno nativo de Windows 11 y planificación de diez sprints
Equipo de 8 integrantes · Cuatro versiones · Repositorio único en GitHub
Propósito y resultado esperado
Construir y evaluar cuatro ejecutables que resuelvan la misma multiplicación de matrices: C secuencial, C paralelo con MPI y OpenMP, Go secuencial y Go paralelo con goroutines. Esta guía define la instalación, la estructura de carpetas, el contrato común de los programas, las pruebas y un plan de trabajo equilibrado hasta obtener resultados reproducibles.
El desarrollo y las mediciones principales se realizarán en Windows 11 de 64 bits sobre procesadores Intel o AMD. No se requiere WSL, una máquina virtual ni Linux. La adaptación a Linux se describe únicamente al final como posibilidad futura.

Entorno común del equipo
Utilizar la misma versión estable de MSVC, del SDK de Windows, de MS-MPI y de Go. No es imprescindible instalar la versión más reciente: sí es imprescindible registrar y mantener las mismas versiones durante la campaña de medición. Los ejemplos usan el compilador cl y el lanzador mpiexec de MS-MPI.
La ruta recomendada es C:\proyectos\matrices-paralelas. Evitar directorios de instalación, carpetas sincronizadas durante las pruebas y nombres de rutas innecesariamente largos. Los comandos se ejecutan desde la raíz del repositorio salvo indicación explícita.
Terminales sin ambigüedad
Para compilar C se utilizará x64 Native Tools Command Prompt, que es una consola CMD preparada por Visual Studio. Desde esa consola se puede ejecutar powershell -NoProfile para abrir PowerShell conservando el entorno x64. Todos los bloques de comandos de esta guía usan esa sesión de PowerShell, excepto la línea que indica cómo abrirla.
En PowerShell las variables se escriben como $env:MSMPI_INC; en CMD serían %MSMPI_INC%. No mezclar ambas sintaxis. Las líneas de compilación que terminan en acento grave (`) continúan en la línea siguiente; no agregar espacios después de ese carácter.
Capacidad y alcance de la primera entrega
Un equipo de cuatro o más núcleos y 8 GB de RAM permite desarrollar y probar tamaños moderados; 16 GB ofrecen más margen. Comenzar con matrices pequeñas. Reservar matrices de 4096 o más para el piloto de capacidad: el consumo del sistema, los procesos MPI y las copias de datos también cuentan.
Go paralelo trabajará dentro de una sola PC. La demostración distribuida, cuando se requiera por la rúbrica, corresponderá al híbrido C. Ejecutar varios procesos MPI en una PC demuestra MPI, pero no demuestra distribución entre varias computadoras.
Relación con la rúbrica
El híbrido MPI y OpenMP cubre la combinación de paradigmas. Las cuatro versiones permiten comparar resultados y tiempos. El equipo deberá seleccionar al menos un artículo IEEE proporcionado por el curso o equivalente y documentar una decisión técnica respaldada por él; las páginas de instalación no sustituyen ese respaldo académico.

2 Instalar C y OpenMP en Windows 11
Puedes trabajar completamente en Visual Studio Code. Instala las extensiones C/C++ de Microsoft y Go. VS Code es el editor: también necesitas Build Tools para compilar C con OpenMP, MS-MPI Runtime y SDK para MPI, y Go para sus dos versiones. No necesitas el IDE completo de Visual Studio; puedes compilar y ejecutar desde la terminal integrada de VS Code. [1]
Paso 1 Instalar las herramientas de compilación
Abrir la página oficial de Visual Studio y descargar Build Tools para Visual Studio. Si ya se tiene Visual Studio con las herramientas de C y C++, usar el instalador para modificar esa instalación. No es necesario instalar una segunda copia. [1]
En Visual Studio Installer, marcar Desarrollo para el escritorio con C++. Confirmar que estén seleccionadas las herramientas MSVC para x64 y x86 y un SDK de Windows compatible. Instalar y cerrar las terminales que estuvieran abiertas antes de la instalación.
Aunque la carga de trabajo diga C++, también instala el compilador de C. Los archivos del proyecto tendrán extensión .c y se compilarán con /TC para hacer explícito el lenguaje. El equipo utilizará C estándar compatible con MSVC y evitará arreglos de longitud variable en la pila.
Paso 2 Abrir una consola x64
En Inicio, buscar x64 Native Tools Command Prompt de la versión instalada. Abrirla y escribir la siguiente línea. La nueva sesión de PowerShell heredará la configuración del compilador. [1]
powershell -NoProfile
 
En la sesión resultante, comprobar:
where.exe cl
cl
$env:VSCMD_ARG_TGT_ARCH
 
Debe encontrarse cl.exe y la arquitectura debe ser x64. Invocar cl sin archivos muestra la información del compilador y puede terminar con un aviso de falta de archivo; eso no es una prueba de compilación fallida.
Paso 3 Activar OpenMP al compilar
OpenMP se habilita con /openmp. No se descarga como un programa independiente para esta ruta de MSVC. Usar únicamente construcciones compatibles con el soporte clásico, como parallel for, private, reduction y schedule(static). El soporte de /openmp se basa en OpenMP 2.0; no basar el proyecto en task, collapse ni funciones de versiones más nuevas. [2]

Paso 4 Editor y runtime
Visual Studio puede servir como editor y depurador. Si prefieren VS Code, instalarlo desde su página oficial y añadir las extensiones C/C++ de Microsoft y Go. Las extensiones no reemplazan los compiladores. Abrir VS Code desde la consola preparada permite heredar el entorno.
Si se ejecuta un binario C en otra PC sin herramientas de desarrollo, instalar el Microsoft Visual C++ Redistributable x64 compatible con la versión del compilador, además del runtime de MS-MPI cuando corresponda. 3 Instalar MS MPI y comprobar C paralelo
Descargar MS-MPI desde Microsoft e instalar los dos componentes: msmpisetup.exe para ejecutar programas MPI y msmpisdk.msi para compilar con mpi.h y msmpi.lib. En la página consultada se ofrece MS-MPI 10.1.3. Cerrar y volver a abrir la consola x64 y PowerShell después de instalar. [4]
where.exe mpiexec
$env:MSMPI_INC
$env:MSMPI_LIB64
Test-Path "$env:MSMPI_INC\mpi.h"
Test-Path "$env:MSMPI_LIB64\msmpi.lib"
mpiexec /?
 
Ambos Test-Path deben devolver True. Si no aparecen las variables, revisar que se instaló el SDK. Las ubicaciones habituales son Microsoft SDKs\MPI\Include y Microsoft SDKs\MPI\Lib\x64 dentro de Program Files (x86); verificar la instalación real antes de cambiar rutas.
Prueba mínima del compilador y los hilos
Guardar el siguiente contenido en smoke_hibrido.c dentro de una carpeta temporal. Es una prueba de instalación, no una de las cuatro versiones finales.
#include <stdio.h>
#include <mpi.h>
#include <omp.h>
int main(int argc, char **argv) {
    int rank, provided, total = 0;
    MPI_Init_thread(&argc, &argv,
                    MPI_THREAD_FUNNELED, &provided);
    if (provided < MPI_THREAD_FUNNELED) {
        MPI_Abort(MPI_COMM_WORLD, 1);
        return 1;
    }
    MPI_Comm_rank(MPI_COMM_WORLD, &rank);
    #pragma omp parallel reduction(+:total)
    {
        total += 1;
    }
    printf("Proceso %d: %d hilos\n", rank, total);
    MPI_Finalize();
    return 0;
}
 
cl /nologo /TC /W4 /O2 /openmp `
  /I "$env:MSMPI_INC" smoke_hibrido.c `
  /Fe:smoke_hibrido.exe /link `
  /LIBPATH:"$env:MSMPI_LIB64" msmpi.lib
$env:OMP_NUM_THREADS = "2"
$env:OMP_DYNAMIC = "FALSE"
mpiexec -n 2 .\smoke_hibrido.exe
 
Resultado esperado: dos mensajes, de los procesos 0 y 1, indicando dos hilos cada uno. El orden puede variar. FUNNELED exige que las llamadas MPI permanezcan en el hilo que inicializó MPI; en el proyecto se harán fuera de las regiones OpenMP. [5]

4 Instalar Go y comprobar el entorno
Paso 1 Instalar Go para Windows
Abrir go.dev/dl, elegir el instalador .msi estable para Windows amd64 y seguir el asistente. La arquitectura amd64 corresponde a Intel y AMD de 64 bits. Mantener la ruta predeterminada salvo necesidad concreta. Cerrar las terminales y volver a abrir la consola de trabajo. [6]
go version
go env GOOS GOARCH GOROOT
where.exe go
 
Se espera GOOS=windows y GOARCH=amd64. No configurar GOROOT manualmente. Todos los integrantes deben acordar una versión exacta de Go y registrar la salida de go version antes de medir.
Paso 2 Prueba mínima
En una carpeta temporal distinta de la prueba de C, guardar main.go con el siguiente contenido:
package main

import (
    "fmt"
    "sync"
)

func main() {
    var wg sync.WaitGroup
    for i := 0; i < 2; i++ {
        wg.Add(1)
        go func(id int) {
            defer wg.Done()
            fmt.Println("Trabajador", id)
        }(i)
    }
    wg.Wait()
}
 
go mod init smoke-go
go fmt ./...
go build -o smoke_go.exe .
.\smoke_go.exe
 
Deben aparecer los trabajadores 0 y 1, posiblemente en distinto orden. Esta prueba confirma que Go compila y sincroniza goroutines; no mide rendimiento.
Paso 3 Herramientas de trabajo
La implementación Go usará únicamente la biblioteca estándar: flag para argumentos, sync para esperar trabajadores, time para tiempos, encoding/csv para resultados y runtime para el paralelismo del runtime. No necesita enlaces con MS-MPI, OpenMP ni cgo.
Usar go fmt, go vet y go test en cada módulo. El detector go test -race es una comprobación adicional: en Windows exige un compilador C compatible con cgo, que MSVC por sí solo no proporciona. No se incluye esa instalación en el entorno básico ni se ejecutan benchmarks con -race. [7]
La variable GOMAXPROCS limita cuántos hilos del runtime pueden ejecutar código Go simultáneamente; no fija por sí sola la cantidad de goroutines. El programa recibirá también --workers para controlar el número de trabajadores de cálculo.

10 Contrato común y diseño de los programas
Entradas y salidas acordadas
La primera entrega multiplicará matrices cuadradas densas de dimensión N, con double en C y float64 en Go. Almacenamiento contiguo por filas. Argumentos obligatorios del contrato: --n y --seed; Go paralelo añade --workers. Los errores se escriben en stderr, los resultados de medición en stdout y las ejecuciones fallidas devuelven un código distinto de cero.
Añadir --input para cargar un fixture de texto común y --output para guardar C cuando se comprueben casos pequeños. Definir el formato en docs/formato-datos.md: primera línea N, luego N filas de A y N filas de B, números separados por espacios y punto decimal. El archivo de salida contiene N y las N filas de C. No imprimir matrices grandes durante el benchmark.
Para generar datos equivalentes, especificar un único generador entero portable o una fórmula determinista de índices y semilla. No asumir que rand de C y math/rand de Go producen la misma secuencia con la misma semilla. Validar con hashes de las entradas o comparación de fixtures.
Núcleo secuencial y Go paralelo
Comenzar con el mismo orden de bucles i, k, j en las cuatro versiones. Cada fila de C se inicializa a cero antes de acumular productos. En Go paralelo, repartir intervalos de filas a un conjunto fijo de workers mediante un canal de tareas; esperar con WaitGroup. A y B serán de solo lectura. Un único trabajador será dueño de cada fila de C. No crear una goroutine por celda.
Híbrido C con MPI y OpenMP
El proceso 0 prepara A y B. MPI_Bcast distribuye B, MPI_Scatterv reparte filas de A y MPI_Gatherv reúne las filas de C. Dentro de cada proceso, parallel for con schedule(static) reparte las filas locales. Mantener MPI fuera de esa región y comprobar el nivel MPI_THREAD_FUNNELED. [5]
Para repartir N filas entre P procesos: q es N dividido enteramente entre P y r es su resto. Los primeros r procesos reciben q+1 filas, los demás q. Los counts de Scatterv y Gatherv se expresan en elementos double: filas locales por N. Los desplazamientos son acumulados de esos counts. Probar también N no divisible entre P y P mayor que N.
Memoria y errores
Reservar matrices en el heap, comprobar fallos y usar size_t para tamaños de memoria. El proceso raíz conserva matrices completas; cada proceso necesita B y sus bloques locales. No estimar el consumo distribuido solo como tres matrices. Validar que counts y desplazamientos quepan en los enteros de las API MPI usadas.
Si un proceso detecta un fallo irrecuperable, evitar que los demás esperen indefinidamente: usar una decisión colectiva de error o MPI_Abort. Liberar los buffers y terminar MPI en el camino normal. En MSVC clásico, usar un índice entero con signo para el bucle OpenMP y declarar las variables de trabajo dentro de su alcance privado.

11 Pruebas y protocolo de medición
Corrección antes de rendimiento
Incluir: N=1; identidad; matriz cero; valores negativos; producto conocido 2 por 2; N impar; particiones no divisibles; más procesos o workers que filas; argumentos inválidos y capacidad insuficiente. Para A=[1 2; 3 4] y B=[5 6; 7 8], el producto esperado es [19 22; 43 50].
Comparar cada elemento con una referencia de confianza: error absoluto menor o igual que atol más rtol por el valor absoluto esperado. Usar inicialmente atol=1e-9 y rtol=1e-9 y justificar ajustes según magnitud y dimensión. Rechazar NaN e infinitos inesperados. Un checksum no sustituye una comparación completa en los fixtures.
Qué se medirá
Registrar kernel_s para el cálculo puro y total_s para el trabajo algorítmico. En total_s las entradas ya están preparadas; incluir el vaciado de C, el reparto, la sincronización de trabajadores, el cálculo y la reunión. Excluir lectura de disco, generación de datos, validación y escritura del CSV. Aplicar límites equivalentes en las cuatro versiones.
En C secuencial usar QueryPerformanceCounter y QueryPerformanceFrequency; en Go, time.Now y time.Since. En MPI usar MPI_Wtime, sincronizar el inicio y obtener con MPI_Reduce y MPI_MAX el mayor tiempo de los procesos. El cronómetro total MPI incluye Bcast, Scatterv, cálculo y Gatherv. Registrar por separado el arranque del lanzador si se desea evaluar latencia de extremo a extremo. [10]
Campaña base
Ejecutar primero un piloto con N=256, 512 y 1024. Para la campaña proponer N=512, 1024 y 2048; añadir 4096 solo si hay memoria y tiempo. Hacer una repetición de calentamiento descartada y cinco repeticiones medidas por configuración. Alternar el orden de las configuraciones entre rondas. No ejecutar dos benchmarks a la vez en una PC.
Probar presupuestos de 1, 2 y 4 trabajadores, y 8 solo si el hardware lo permite. En C explorar combinaciones P por T como 1 por 4, 2 por 2 y 4 por 1 con el mismo presupuesto. En Go usar workers y GOMAXPROCS coherentes. Registrar CPU, RAM, versiones, commit, N, semilla, P, T, workers, GOMAXPROCS, repetición, kernel_s, total_s y estado de validación.
Interpretación y gráficos
Calcular speedup como tiempo secuencial dividido entre tiempo paralelo del mismo lenguaje, usando la mediana de total_s. Eficiencia: speedup dividido entre P por T para C o entre workers para Go, declarando el recurso nominal. Añadir dispersión mediante mínimo y máximo o intervalo intercuartílico. Comparar C y Go mediante tiempos absolutos; no atribuir toda diferencia únicamente al lenguaje.
Entregar gráficos de tiempo frente a N, speedup frente a trabajadores y efecto de P y T. Si el paralelo no mejora, conservar los datos y explicar el sobrecoste. No fijar una aceleración mínima inventada para aprobar el trabajo.

Alcance distribuido en Windows
La campaña base funciona en una sola PC con Windows 11. Si el docente exige varios nodos físicos, el híbrido C debe ejecutarse en dos o más PCs Windows de la misma arquitectura. Instalar el mismo runtime MS-MPI y el runtime de Visual C++ en cada una, distribuir el mismo ejecutable y usar una red local autorizada.
MS-MPI entre equipos necesita configuración adicional del servicio o administrador de procesos, autenticación y reglas de red. Consultar mpiexec /? y smpd -help de la versión instalada; las opciones y políticas del laboratorio determinan el mecanismo de arranque. Verificar primero un programa que imprima el nombre del equipo y el rank, antes de intentar multiplicar matrices. No asumir que la ejecución local valida el despliegue remoto.
Registrar el número de núcleos de cada nodo y no sobreasignar hilos. Incluir latencia de red y comunicación en total_s. Mantener esta campaña separada de la de una PC. Si no se dispone de varios equipos, declarar la limitación en el informe en vez de afirmar que los procesos locales constituyen un clúster físico.
Riesgos de planificación que se deben resolver pronto
En S1 se confirma disponibilidad de PCs y si la rúbrica acepta el alcance local. En S2 se fija el formato y el generador para evitar discrepancias entre lenguajes. En S6 se decide si alguna optimización merece seguir; en S7 se congela el código. Cualquier arreglo posterior que modifique el cálculo obliga a repetir los lotes afectados.
Las 640 horas son una estimación inicial de trabajo activo. Si una tarea excede sus 6 horas principales, dividirla y reducir alcance opcional, manteniendo corrección, mediciones y documentación. La distribución será equitativa por esfuerzo real registrado, además de por horas previstas.

15 Posible adaptación futura a Linux
Sí, las cuatro versiones pueden adaptarse a una distribución Linux, por ejemplo Ubuntu, Debian o Fedora. La mayor parte del algoritmo, el reparto de filas MPI y el código de goroutines puede conservarse si desde el inicio se separan los detalles del sistema operativo. Esta sección describe cambios posibles; no instala ni implementa nada para Linux.
Componente
Cambio que sería necesario
Compilador de C
Sustituir MSVC por GCC o Clang. Cambiar las opciones de compilación y generar binarios Linux; un .exe de Windows no es el binario nativo que se entregaría allí.
MPI
Sustituir MS-MPI por Open MPI o MPICH. Recompilar contra las cabeceras y bibliotecas de la implementación elegida y adaptar las opciones del lanzador.
OpenMP
Conservar las directivas compatibles. Con GCC se habilita mediante -fopenmp, en lugar de /openmp. Revisar opciones de afinidad y número de hilos. [11]
Cronómetro C secuencial
Reemplazar QueryPerformanceCounter por un reloj monotónico disponible en Linux, detrás de una función de cronometraje común. El núcleo matemático no debería incluir windows.h.
Go
Instalar Go para Linux y recompilar ambos módulos. Con biblioteca estándar y rutas portables, el núcleo secuencial y los workers no deberían requerir cambios funcionales.
Scripts y rutas
Adaptar los scripts de compilación y medición a Bash, Make o PowerShell multiplataforma. Cambiar rutas, separadores y asignación de variables de entorno.
Despliegue MPI
Configurar comunicación y arranque de procesos según Open MPI o MPICH, por ejemplo con SSH y un archivo de hosts cuando corresponda. No reutilizar reglas específicas de MS-MPI. [12]
Validación y mediciones
Volver a ejecutar fixtures, revisar tolerancias y repetir la campaña completa registrando sistema, compilador y runtime. No combinar tiempos Windows y Linux como si fueran una misma condición.

Decisiones actuales que facilitan esa adaptación
Mantener el núcleo de matrices independiente del cronómetro, usar memoria contigua y tipos de tamaño apropiado, construir rutas con funciones del lenguaje y no invocar comandos de Windows desde el algoritmo. MPI y OpenMP deben limitarse al módulo paralelo; Go debe mantener separados el cálculo y la lectura de archivos.
El repositorio seguiría conservando las mismas cuatro carpetas. En una etapa futura se añadirían instrucciones y scripts específicos para Linux junto con nuevos resultados etiquetados por plataforma. No sería necesario convertir este proyecto en ocho versiones del algoritmo.
